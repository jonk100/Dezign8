# Color System

This document outlines how color is managed in this design system. It details the color architecture, color roles, the 7-step semantic step system, and the lifecycle of color properties from tokens through TypeScript to CSS.

---

## The 3-Layer Color Architecture

Colors are structured in three distinct layers to isolate raw palette choices from layout-specific component overrides.

```
+------------------------------------------------------------+
| Layer 1: Raw Palette Colors (color-vars.css)              |
| E.g., --cyan-15, --red-40                                 |
+------------------------------------------------------------+
                             |
                             v
+------------------------------------------------------------+
| Layer 2: Semantic Roles & Steps (tokens-color.css)        |
| E.g., --primary--base, --danger--subtle                    |
+------------------------------------------------------------+
                             |
                             v
+------------------------------------------------------------+
| Layer 3: Component-Scoped Channels (Component CSS)        |
| E.g., --control--color-base, --surface--bg                 |
+------------------------------------------------------------+
```

1. **Layer 1: Raw Palette Colors (`color-vars.css`):** Absolute color values defined in OKLCH. They have no semantic meaning and do not change between themes.
2. **Layer 2: Semantic Roles & Steps (`tokens-color.css`):** Theme-aware variables (changing value between light and dark modes) that represent a specific role and step name (e.g., `--primary--base` or `--danger--subtle`).
3. **Layer 3: Component-Scoped Channels (Component CSS):** Component-level CSS variables generated by component hooks (e.g., `--button-bg` or `--surface--bg`). Component CSS stylesheets read **only** from Layer 3, leaving them decoupled from the active color role.

## Semantic Steps (The 7-Step Model)

Every color role exposes the same 7 named steps. Each step is calibrated for a specific interactive or layout concern:

```
subtle   ░░░░░░░░░░  Very light tint. Background for soft/tinted elements.
muted    ▒▒▒▒▒▒▒▒▒▒  Soft tint. Hover background on soft variants.
base     ██████████  The color. Solid fills, active borders.
vivid    ██████████▌ Slightly brighter/deeper. Hover on solid elements.
deep     ████████▓▓  Dark shade. Pressed states, heavy emphasis.
border   ▓▓▓▓▓▓      Between muted and base. Outlined borders.
text     ████         Readable foreground on neutral backgrounds.
```

| Step | Common Usage | Example |
|---|---|---|
| `subtle` | Fills for soft, tinted elements (Badges, Chip fills, Toast backgrounds) | `var(--primary--subtle)` |
| `muted` | Hover states for soft/tinted elements | `var(--primary--muted)` |
| `base` | Solid fills, active border outlines | `var(--primary--base)` |
| `vivid` | Hover states for solid elements | `var(--primary--vivid)` |
| `deep` | Active/pressed state backgrounds, heavy foreground highlights | `var(--primary--deep)` |
| `border` | Borders of outlined or dashed variants | `var(--primary--border)` |
| `text` | Colored text or icons on neutral backgrounds | `var(--primary--text)` |

## Color Roles

There are three categories of color roles available across the design system:

### 1. Accent Roles
Designed for interactive UI chrome and brand accents:
* `primary` (cyan palette): Main CTA buttons, links, active navigation items.
* `secondary` (purple palette): Alternative actions, auxiliary navigation.
* `accent` (lime palette): Decorative badges, highlight callouts.

### 2. Semantic Roles
Used to communicate status, warnings, and confirmations:
* `danger` (red palette): Destructive buttons, error alerts, validation issues.
* `warning` (orange palette): Warning banners, degraded system states.
* `success` (green/lime palette): Success notifications, completion checks.

### 3. Neutral Role
Used for structural hierarchy, cards, and subtle panels. Neutral maps directly to the surface and border tokens rather than a color palette, meaning it stays automatically on-theme in both light and dark mode:
```typescript
neutral: {
  subtle: "var(--bg--3)",
  muted:  "var(--bg--4)",
  base:   "var(--border--strong)",
  vivid:  "var(--border--strong)",
  deep:   "var(--text--secondary)",
  border: "var(--border--default)",
  text:   "var(--text--secondary)",
}
```

## Special Color Tokens

### `--text--on-color`
This is a special utility token used to ensure accessible contrast for text rendered **on top of** a solid background (such as a solid button or a filled badge). In both light and dark mode, it resolves to a dark slate to maximize contrast.

```css
.button--solid {
  background-color: var(--button-bg, var(--primary-base));
  color: var(--text--on-color); /* Near-black slate in both themes */
}
```

## Lifecycle of a Color Prop

Here is how a color property resolves from the consumer to the DOM:

1. **Prop Definition:**
   The component declares a `color` prop (e.g. `<Button color="danger" variant="soft">`).
2. **Hook Resolution:**
   The component hook destructures `color` and passes it to `resolveColorChannels(color, "button")` (or `resolveColorRole(color, "bg")` inside `useBaseCompose` for background properties).
3. **CSS Variable Generation:**
   The helper emits a set of 7 variables in the `style` return object:
   ```css
   --button--color-subtle: var(--danger--subtle);
   --button--color-muted:  var(--danger--muted);
   --button--color-base:   var(--danger--base);
   ...
   ```
4. **CSS Consumption:**
   The component stylesheet applies these variables:
   ```css
   .button--soft {
     background-color: var(--button--color-subtle);
     color:            var(--button--color-text);
   }
   ```
5. **Dynamic Updates:**
   If you change the prop to `color="success"`, the hook generates the exact same custom variable names but binds them to `--success--subtle` instead. The stylesheet never changes.
